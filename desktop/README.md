# فردای روشن — آغاز بازسازی دسکتاپ

این پوشه نسخهٔ اولیه‌ای در کنار برنامهٔ PHP است، نه جایگزین آمادهٔ استفاده. برنامه و دیتابیس قبلی دست‌نخورده‌اند. **از این نسخه برای معلومات واقعی شرکت استفاده نکنید:** احراز هویت، ورود اطلاعات قبلی، مدیریت کامل اسناد، تنظیمات کامل تقویم و سایر شیت‌ها تکمیل نشده‌اند.

## آنچه پیاده‌سازی شده

- React/TypeScript و رابط راست‌چین با فونت محلی؛ لایهٔ `Store` میان رابط و روش دسترسی به داده.
- Tauri 2 و Rust/SQLx با SQLite جداگانه در پوشهٔ دادهٔ برنامهٔ کاربر، همراه migration و کلید خارجی فعال.
- ثبت و ویرایش اطلاعات اولیهٔ کارمندان با امکان غیرفعال‌سازی.
- ثبت و ویرایش انفرادی حضور و غیاب در شش وضعیت، با ساعت اختیاری و اضافه‌کاری؛ هر کارمند در هر تاریخ فقط یک رکورد دارد. فهرست فیلتر تاریخ، کارمند و وضعیت و خلاصهٔ رکوردهای نمایش‌داده‌شده دارد؛ روزهای ثبت‌نشده در خلاصه محاسبه نمی‌شوند و تغییر تقویم فیلترها را پاک می‌کند. ورق روزانه رکوردهای انتخاب‌شدهٔ کارمندان فعال و بدون رکورد را به صورت اتمی ثبت می‌کند و رکوردهای قبلی را بازنویسی نمی‌کند؛ ساعت خالی و اضافه‌کاری صفر است. حذف، گزارش ماهانه و اتصال به معاش هنوز وجود ندارند.
- ثبت و ویرایش معاش با نگهداری مبلغ پایهٔ زمان ثبت، پاداش، جریمه و اضافه‌کاری به صدم افغانی؛ دوره دارای تقویم مستقل و تاریخ پرداخت ISO است. مطابق فرمول نسخهٔ قدیم مجموع منفی مجاز است و هشدار می‌گیرد. فهرست معاش فیلتر تاریخ پرداخت، کارمند، روش پرداخت و مجموع موارد نمایش‌داده‌شده دارد؛ با تغییر تقویم فیلترهای آن پاک می‌شوند. هشدار غیرمسدودکننده برای دورهٔ تکراری در فهرست فعلی وجود دارد، اما تضمین عدم ثبت تکراری یا کنترل هم‌زمان وجود ندارد. شماره سند، چاپ، حساب دخل و فهرست مشترک پرداخت‌کنندگان هنوز وجود ندارد و نام/کد کارمند از اطلاعات فعلی خوانده می‌شود.
- ثبت و ویرایش مصارف با دو مبلغ مستقل افغانی و دالری، تاریخ، شرح، نوع، فروشگاه، بل، پرداخت‌کننده، روش پرداخت و توضیحات؛ فیلتر بازهٔ تاریخ و مجموع مجزای ارزهای موارد نمایش‌داده‌شده شامل نقده و باقی است؛ با تغییر تقویم فیلترهای صفحه پاک می‌شوند. هنوز شمارهٔ سند، حساب دخل و فهرست‌های مشترک انواع و پرداخت‌کنندگان وجود ندارد.
- ثبت اولیهٔ مشتری، فروش و رسید، فهرست صفحه‌بندی‌شدهٔ جداگانهٔ فروش و رسید با جستجو و فیلتر تاریخ، مشتری و نوع پرداخت یا منبع رسید، و کارت حساب بر اساس فروش قرضه و رسیدهای مؤثر؛ امانت در کارت نمایش داده می‌شود اما از بدهی کم نمی‌شود.
- مبلغ و حجم به شکل عدد صحیح مقیاس‌دار نگهداری می‌شوند و مجموع فروش در Rust دوباره محاسبه می‌شود. ورود و نمایش تاریخ در فرم‌های فروش و رسید به شمسی یا میلادی است؛ مقدار ارسالی و ذخیره‌شده میلادی `YYYY-MM-DD` است. تاریخ امروز براساس ساعت کابل تعیین می‌شود.
- سرویس SQLite از فرمان‌های Tauri جدا شده است؛ این فقط یک گام معماری است و هنوز به معنی پیاده‌سازی سرور یا پشتیبانی از PostgreSQL نیست.
- پشتیبان و بازگردانی آزمایشی SQLite: فایل با `VACUUM INTO` ساخته می‌شود؛ بازگردانی نسخه‌های ساختار ۱، ۲، ۳، ۴ و ۵ را می‌پذیرد، پیش از تغییر یک نسخهٔ ایمنی می‌سازد و همهٔ جایگزینی‌ها را در یک تراکنش انجام می‌دهد. این فایل‌ها رمزگذاری نشده‌اند و نباید تنها نسخهٔ اطلاعات واقعی باشند.
- شناسه‌های مستقل UUID؛ شمارهٔ سند رسمی و تمام فیلدهای نسخهٔ قدیمی هنوز پیاده‌سازی نشده‌اند.

## اجرا

Node.js و npm و ابزار Rust و پیش‌نیازهای Tauri 2 برای سیستم‌عامل مقصد لازم‌اند. در Linux، کتابخانه‌های توسعهٔ WebKitGTK و سایر پیش‌نیازهای رسمی Tauri نیز لازم است. از داخل این پوشه:

```sh
npm ci
npm run tauri dev
```

برای مشاهدهٔ رابط بدون Rust: `npm run dev`؛ مرورگر تنها یک پیش‌نمایش **حافظه‌ای و موقت** با اطلاعات نمونه است. با تازه‌کردن صفحه داده‌ها از بین می‌روند و هیچ ارتباطی با دیتابیس PHP یا SQLite ندارد. نسخهٔ تولیدی وب/API هنوز وجود ندارد.

```sh
npm test
npm run build
python3 tests/schema_test.py
npx playwright install chromium
npm run test:e2e
cd src-tauri && cargo test
```

تست مرورگر فقط پیش‌نمایش موقت را بررسی می‌کند، نه اتصال Tauri و SQLite. تست Rust در GitHub Actions برای Windows تنظیم شده است اما تا زمان اجرای واقعی آن نتیجه‌ای تضمین نشده است.

## گام‌های بعدی و معماری

قوانین حسابداری، سال مالی و انتقال داده باید با نمونهٔ واقعی و حسابدار تأیید شود. برای حالت آنلاین، سرویس مرکزی، مجوزها، لایهٔ ذخیرهٔ سروری و قرارداد API باید جداگانه پیاده‌سازی و آزمایش شوند؛ هیچ همگام‌سازی یا پشتیبانی چندکاربره وجود ندارد. پیش از استفادهٔ واقعی به تست یکپارچهٔ پنجرهٔ Tauri و SQLite، آزمایش بیشتر بازیابی، شماره‌گذاری سند و تطبیق کامل گزارش‌ها نیاز است.

## بازگردانی آزمایشی

بازگردانی فقط فایل `.sqlite3` ساخت همین نسخهٔ دسکتاپ را می‌پذیرد، نه بکاپ SQL مربوط به PHP/MySQL. ساختار جدول‌ها، سابقهٔ migration، صحت SQLite، ارتباطات و بخشی از قواعد مالی بررسی می‌شوند. قبل از جایگزینی، یک فایل ایمنی در پوشهٔ `restore-safety` در پوشهٔ دادهٔ برنامه ساخته و مسیر آن پس از موفقیت نمایش داده می‌شود. در صورت خطا، تراکنش بازگردانده می‌شود؛ فایل ایمنی بدون رمزگذاری باقی می‌ماند. فایل‌های نسخه‌های آینده تا زمان پشتیبانی صریح، رد می‌شوند. در بازگردانی نسخهٔ ۱، جدول کارمندان در فایل قدیمی وجود ندارد و کارمندان فعلی پس از هشدار حذف می‌شوند؛ نسخهٔ ایمنی پیش از بازگردانی آن‌ها را حفظ می‌کند. فایل‌های نسخهٔ ۱ و ۲ جدول مصارف ندارند؛ بازگردانی آن‌ها پس از هشدار، مصارف فعلی را جایگزین و فقط در نسخهٔ ایمنی حفظ می‌کند. فایل‌های نسخهٔ ۱ تا ۳ جدول معاش ندارند؛ با بازگردانی آن‌ها معاشات فعلی پس از هشدار حذف و در نسخهٔ ایمنی حفظ می‌شوند. فایل‌های نسخهٔ ۱ تا ۴ جدول حضور و غیاب ندارند؛ بازگردانی آن‌ها رکوردهای فعلی را پس از هشدار پاک می‌کند و نسخهٔ ایمنی آن‌ها را حفظ می‌کند. اطلاعات پیش‌نمایش مرورگر در این عملیات نقشی ندارند. هنوز نباید از برنامه برای اطلاعات واقعی استفاده کرد.

## تقویم و نسخهٔ اجرایی آزمایشی

انتخاب تقویم فعلاً فقط در طول نشست رابط کاربری نگهداری می‌شود؛ تنظیمات دائمی، سال مالی و تاریخ‌پیکر هنوز پیاده‌سازی نشده‌اند. تاریخ شمسی در بازهٔ مثبت سال‌های ۱ تا ۳۱۷۷ با `jalaali-js` محاسبه می‌شود؛ تاریخ میلادی خارج از محدودهٔ قابل تبدیل، با برچسب «میلادی» نمایش داده می‌شود. این قابلیت جایگزین آزمون گزارش‌های مالی، کبیسه و تبدیل اطلاعات قبلی نیست.

اگر اجرای GitHub Actions موفق باشد، یک فایل اجرایی **آزمایشی، بدون نصب‌کننده و امضای دیجیتال** به مدت هفت روز به عنوان artifact نگهداری می‌شود. برای اجرا Windows و WebView2 لازم است. ساخته‌شدن فایل اجرایی به معنی تست رابط دسکتاپ یا آمادگی برای اطلاعات واقعی نیست.

- ویرایش مشتری کد، نام، تماس و بدهی اولیه را تغییر می‌دهد؛ فروش‌ها و رسیدهای مرتبط حفظ می‌شوند. تغییر بدهی اولیه ماندهٔ حساب و همهٔ مانده‌های جاری کارت حساب را بازحساب می‌کند؛ فعلاً تاریخچهٔ ممیزی تغییرات وجود ندارد.
