# ۱. ماتریس قابلیت‌ها و داده‌های نسخهٔ قدیم

**معیار وضعیت:** «نمونه» یعنی بخشی وجود دارد ولی کامل یا قابل استفادهٔ واقعی نیست؛ «نیست» یعنی در نمونهٔ دسکتاپ قابلیت متناظر مشاهده نشد. این جدول بر اساس بررسی کد است، نه آزمون کامل برنامهٔ قدیم. مسیرها از ریشهٔ مخزن‌اند. فهرست ماشینی هر ستون در `farday-next/contracts/legacy-schema.json` است.

## نگاشت تمام جدول‌ها

| جدول PHP | مسیر مورد نیاز در محصول جدید / اهمیت |
|---|---|
| `company`, `machines` | مشخصات و ماشینری با تمام ستون‌ها، نه صرفاً نام سرصفحه. |
| `settings` | تفکیک تنظیمات نمایش از تنظیمات مالی و نسخه‌گذاری/تاریخ اثر؛ حفظ همهٔ فیلدهای منبع. |
| `employees`, `attendance` | نگاشت شناسه و تمام اطلاعات پرسنلی، زمان‌ها و وضعیت‌ها؛ قواعد حذف و سوابق بررسی شوند. |
| `customers` | همهٔ فیلدها، ماندهٔ اولیه و روابط، حتی مشتری حذف‌شده/ارجاع تهی در اسناد قدیمی. |
| `material_types`, `expense_types`, `payers`, `receipt_sources` | شناسه، نام، واحد/نوع، ترتیب، فعال و `affects_balance`؛ رشتهٔ ساده کافی نیست. تغییر اثر رسید می‌تواند تاریخچه را تغییر دهد و باید تعیین تکلیف شود. |
| `sales`, `expenses`, `receipts`, `salaries` | حفظ شمارهٔ قدیم، ID منبع، زمان‌ها، همهٔ مقادیر decimal و کلیدهای خارجی؛ مقدار ثبت‌شده و مبلغ محاسبه‌شده جدا بررسی شوند. |
| `users` | هویت و وضعیت/نقش با سیاست امن انتقال و بازنشانی؛ هش‌ها و رمزها هرگز در تاریخچهٔ عمومی یا گزارش خطا قرار نگیرند. |
| `counters` | سری و سال و high-water؛ پس از انتقال/بازیابی شمارهٔ تکراری تولید نشود؛ سیاست تغییر تقویم و چند دستگاه لازم است. |
| `report_notes` | دورهٔ متنی قدیم فاقد شناسهٔ مستقل تقویم است؛ تقویم تاریخی باید با شواهد/تصمیم تعیین شود، نه حدس. |
| `activity_log` | نگهداری تاریخچهٔ منبع با شناسه/زمان/نام خام و برچسب قدیمی؛ هویت یا قبل/بعدی که در منبع وجود ندارد جعل نشود. |

منبع حقیقت برای همهٔ ستون‌ها و مقادیر nullable: `database/schema.sql` و manifest ماشینی. تفاوت schema نصب‌شده با مخزن و دادهٔ واقعی باید پیش از انتقال جداگانه بررسی شود.
