# ۳. قواعد، تعارض‌ها و برنامهٔ تطبیق

## روش بررسی

مرجع رفتار، کد PHP **و** نمونه‌های ورودی/خروجی است، نه صرفاً README یا اسکرین‌شات. ابتدا در محیط مجزا MySQL/MariaDB و PHP، schema و seed را نصب و با اطلاعات ساختگی ثابت اجرا کنیم. برای هر سناریو ورودی، نقش، عملیات، وضعیت همهٔ جدول‌های مؤثر، خروجی UI/CSV/چاپ و خطا ثبت شود؛ سپس همان سناریو در Tauri واقعی اجرا شود. اختلافی که ناشی از اشکال منبع است در فهرست جدا و با نظر صاحب کسب‌وکار ثبت شود. این گزارش هنوز اجرای زنده یا تأیید حسابدار نیست.

## ۳.۲ تفاوت‌های شناخته‌شده‌ای که نباید پنهان شوند

1. **کارت مشتری و مانده:** `customer_balance()` فقط رسید مؤثر را کسر می‌کند اما `customer_ledger()` برای رسیدهای داخل بازه همهٔ مبلغ‌ها را به credit می‌گذارد؛ اگر امانت داخل بازه باشد، ماندهٔ پایان کارت و ماندهٔ مشتری می‌توانند متفاوت شوند (`app/reports.php`, توابع ۲۵۵ و ۲۹۴). در مرجع قبل از بازه، رسید غیرمؤثر حذف می‌شود؛ در داخل بازه خیر. باید با دادهٔ ساختگی زنده بازتولید و دربارهٔ اصلاح تأیید گرفته شود.
2. **تغییر شماره در ویرایش:** `crud_handle` برای فیلد auto پیش از `if ($id)` شمارنده را افزایش می‌دهد (`app/crud.php`)، در نتیجه ویرایش می‌تواند شمارهٔ جدید تخصیص دهد. شمارهٔ ثابت معمولاً ایمن‌تر است ولی یک تغییر رفتاری است، نه «عین قدیم». سیاست سند و سناریوی backdated و تغییر سال باید مشخص شود.
3. **افتراق دادهٔ ذخیره‌شده و رابط:** schema اجازهٔ مشتری/منبع NULL برای بعضی سندها دارد، در حالی که فرم برخی را الزامی می‌کند. داده‌های قدیمی و حذف‌شده را نباید خودکار دور ریخت یا به مشتری ساختگی متصل کرد.
4. **تاریخچهٔ منبع:** `log_activity` فقط عملیات و جزئیات کوتاه ذخیره می‌کند و خطای ثبت را نادیده می‌گیرد (`app/util.php`). در حضور، logging پس از commit است (`attendance.php`). ادعای محافظت تغییرناپذیر یا سابقهٔ قبل/بعد دربارهٔ منبع درست نیست.
5. **دسترسی حضور:** صفحه فقط `require_login()` می‌خواهد و شاخهٔ clear در همان handler حذف می‌کند، نه کنترل مدیر مثل CRUD عمومی (`attendance.php`, `app/crud.php`). باید تصمیم بگیریم حذف فقط مدیر باشد؛ با اصلاح، تفاوت ثبت شود.
6. **بازیابی SQL قدیم:** کد خروجی `DROP`/`CREATE` و `INSERT` تولید می‌کند (`app/backup.php`)، ولی بازیابی `;\n` split و statementهای شروع‌شده با `--` را رد می‌کند (`backup.php`)؛ همراه عملیات DDL و بدون مرحلهٔ staging است. صحت و atomicity را نباید بدون بازتولید فرض کرد؛ به عنوان مسیر امن انتقال دوباره اجرا نشود.
7. **نسخهٔ فعلی `desktop/`:** فرمان‌های عملیاتی در `src-tauri/src/lib.rs` مستقیم سرویس‌های بدون guard را صدا می‌زنند؛ نمونه‌های `authorized_*` به فرمان‌ها متصل نیستند. دخل دستی، منابع رسید ثابت و سقف اعداد، هم‌ارز ساختار PHP نیستند. این ریسک فقط با صفحهٔ ورود ظاهری حل نمی‌شود.

## ۳.۳ سناریوی مصنوعی طلایی اولیه (انتظار محاسباتی، هنوز اجرای تطبیقی نشده)

| داده | مقدار |
|---|---|
| ماندهٔ اولیه مشتری | ۱٬۰۰۰٫۰۰ AFN |
| فروش باقی | حجم ۱۰٫۰۰۰ × (قیمت ۵۰۰٫۰۰ + کرایه ۳۰۰٫۰۰) = ۸٬۰۰۰٫۰۰ AFN |
| فروش نقده | ۵۰۰٫۰۰ AFN |
| رسید مؤثر | ۱٬۲۰۰٫۰۰ AFN |
| رسید امانت غیرمؤثر | ۳۰۰٫۰۰ AFN |
| مصارف | ۱۲۰٫۰۰ AFN نقد از دخل + ۸۰٫۰۰ AFN باقی؛ جداگانه ۵٫۰۰ USD |
| معاش | ۷۰٫۰۰ AFN نقد از دخل + ۳۰٫۰۰ AFN حواله |

انتظار بر اساس کد خوانده‌شده (تمام موارد داخل یک بازه، opening cash صفر):

- ماندهٔ مشتری: `۱۰۰۰ + ۸۰۰۰ − ۱۲۰۰ = ۷۸۰۰`؛ امانت اثر ندارد.
- کارت قدیم اگر هر دو رسید **داخل بازه** باشند: `۷۵۰۰` به علت تعارض F-03؛ این خروجی مطلوب محسوب نمی‌شود تا تصمیم ثبت شود.
- تغییر دخل `all`: `۵۰۰ + ۱۵۰۰ − ۲۰۰ − ۱۰۰ = ۱۷۰۰` AFN؛ USD تبدیل نمی‌شود.
- تغییر دخل `cash_only`: `۵۰۰ + ۱۵۰۰ − ۱۲۰ − ۷۰ = ۱۸۱۰` AFN؛ فرض شده پرداخت‌کنندهٔ دو مورد مشخص نوع «دخل» است.
- فرمول سود قدیم: `(۸۰۰۰ + ۵۰۰) − (۲۰۰ + ۱۰۰) = ۸۲۰۰` AFN؛ نه سود تأییدشدهٔ حسابداری.

در تست واقعی، شناسه، پرداخت‌کننده، وضعیت منبع رسید، بازه و مقدار ذخیره‌شده هر مورد مشخص و نتایج UI، SQL، CSV و چاپ مستقل مقایسه شود. سناریو صرفاً برای آزمایش است، نه دادهٔ شرکت.

## ۳.۴ فهرست تست و شروط پذیرش

- **قرارداد داده:** همهٔ ۱۸ جدول و ستون‌ها، nullable/enum، Persian/Arabic digits، Unicode/collation، حداکثر DECIMAL، zero/negative، متن بلند، FK تهی/حذف‌شده؛ بدون حذف/تبدیل خاموش.
- **مالی:** ماتریس `cash|credit × payer kind × source affect × AFN/USD`، بدهکار/بستانکار، امانت، ویرایش/ابطال، مبلغ‌های لب مرز و rounding، cross-check جمع اسناد/راپور/CSV/چاپ. تست مبلغ و حجم تصادفی با عدد صحیح و سناریوی overflow.
- **تاریخ:** همهٔ مرزهای بازه شامل، سال کبیسه شمسی/میلادی، سال مالی با روز غیر اول و تعویض سال، تاریخ صفر/نامعتبر، `Asia/Kabul` و مقایسهٔ نتایج PHP با نسخهٔ جدید؛ سیاست اختلاف‌ها واضح.
- **گردش کار:** تمام فرم‌ها، فیلتر، جستجو، صفحه‌بندی، مرتب‌سازی، کنترل دادهٔ کهنه، لینک‌های وابسته، تمام ستون‌های export و چاپ هر نوع، برای مدیر و کارمند؛ تست حذف/ابطال و سوابق وابسته.
- **امنیت:** دستیابی مستقیم به هر command بدون نشست/نقش مناسب، تغییر نقش/رمز بین تأیید و commit، logout هم‌زمان، brute-force و انقضای نشست، عدم ورود secrets به لاگ، rollback هنگام خرابی audit، restore و export با مجوز. فایل محلی و snapshot بدون ضد‌دستکاری مستقل نباید امن کامل معرفی شوند.
- **پایداری:** commit هم‌زمان، دوبار اجرا، timeout/lock، قطع برق/پروسه، فضای دیسک ناکافی، migration هر نسخه، import مجدد/نیمه‌کاره، backup/restore معیوب و rollback، شمارنده بعد از restore، عدم بازنویسی فایل، محافظت backup.
- **محیط واقعی:** Windows Tauri/WebView2 تعامل کلیک و کیبورد، RTL، فرم‌های بومی file picker، چاپگر/PDF، نصب تعاملی، ارتقا از نسخهٔ قبلی، uninstall و بازنصب، آفلاین/Online WebView2، ارزیابی installer و signature. Playwright مرورگر و smoke process جایگزین این‌ها نیستند.
- **مقیاس و پذیرش:** حجم واقع‌بینانه با هزاران/صدها هزار سند و دادهٔ ساختگی، زمان پاسخ هدف با کاربر تعیین شود؛ مقایسهٔ ردیف/جمع و حسابدار روی نسخهٔ ناشناس از دادهٔ واقعی؛ سناریوهای دفتر شرکت و امضای پذیرش.
