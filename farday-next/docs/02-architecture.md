# ۲. معماری پیشنهادی و نقشهٔ ساخت

## ۲.۱ هدف و مرزبندی

- PHP/MySQL در ریشه مرجع است و تغییر نمی‌کند؛ `desktop/` نمونهٔ مستقل موجود است؛ `farday-next/` پروژهٔ جدید و محل برنامه و اسناد آن خواهد بود. **فعلاً در `farday-next/` فقط بررسی و قرارداد است.**
- برای جلوگیری از اشتراک ناخواستهٔ دیتابیس/نصب با `desktop/`، برنامهٔ آینده باید شناسهٔ Tauri، مسیر داده، نام bundle و نسخه‌بندی جدا داشته باشد؛ پیش از اولین ساخت دربارهٔ انتقال از پیش‌نمایش تصمیم بگیریم. هیچ فایل دیتابیس را خودکار جایگزین نکنیم.
- پیشنهاد معماری: `React/TS UI → IPC typed → Tauri commands → Rust application services (validation/authorization/transactions) → SQLx repositories → SQLite local`. منطق مالی، مجوز و شمارهٔ سند فقط در Rust انجام و UI نتایج را نمایش دهد. از منابع UI قدیمی می‌توان با آزمون استفاده کرد، نه اینکه UI به طور مستقل مبنای مالی شود.
- `domain` شامل پول/تاریخ/قواعد مستقل از Tauri؛ `application` شامل use-case و مجوز؛ `infrastructure` شامل SQLx و فایل؛ `commands` آداپتور باریک؛ `ui` و `tests` جدا. قرارداد DTO versioned و خطاهای قابل فهم؛ رشته‌های مالی decimal نه float JSON.

## ۲.۲ تصمیم فناوری و محدودیت‌ها

| فناوری | نقش پیشنهادی | نکتهٔ طراحی |
|---|---|---|
| Tauri 2 | پنجره، IPC و بسته‌بندی | capability محدود به پنجره و permission لازم؛ CSP؛ عدم بارگذاری محتوای دوردست قابل اعتماد به اشتباه؛ فرمان‌های Rust خودشان مجوز نقش/داده را بررسی کنند. Scope در فرمان سفارشی باید توسط پیاده‌سازی اعمال شود [3](https://v2.tauri.app/security/scope/). |
| React + TypeScript | رابط RTL، فرم‌ها، راهبری و نمایش | validation سمت رابط برای تجربهٔ کاربر است، نه مرز امنیت؛ نمایش مبلغ/تاریخ و error، تست دسترس‌پذیری و بدون دستکاری DOM ناامن. |
| Rust + SQLx | قواعد، تراکنش، ارتباط داده | کوئری پارامتری، migration نسخه‌دار، خطاهای اتمی و تست با دیتابیس واقعی؛ SQLx migration و backendهای مختلف دارد، اما سازگاری query/schema بین SQLite و PostgreSQL خودکار نیست [1](https://github.com/launchbadge/sqlx). |
| SQLite محلی | حالت تک‌دستگاه/چند نشست محلی | foreign keys روی هر اتصال؛ تراکنش صریح، busy timeout و سیاست journal/durability پس از آزمون. WAL خواندن هم‌زمان را بهتر می‌کند اما یک نویسنده دارد و برای فایل شبکه مناسب نیست [1](https://www.sqlite.org/wal.html). `desktop/` فعلی `max_connections(1)` دارد و WAL را صریح فعال نمی‌کند (`service.rs`). |
| سرویس مرکزی + PostgreSQL یا MySQL | گزینهٔ آینده اگر هم‌زمانی چند دستگاه لازم است | سرور مورد اعتماد، auth، backup، ارتباط امن، migration و سازگاری مستقل؛ Tauri فقط client است. نگاشت و مقایسه و conflict policy آزمون می‌خواهد؛ SQLite روی پوشهٔ اشتراکی را sync معرفی نکنیم [4](https://www.sqlite.org/whentouse.html). |

**مقایسهٔ سه راه:** (الف) SQLite کاملاً محلی: کم‌هزینه و آفلاین اما بدون چند دستگاه مشترک؛ (ب) سرور مرکزی + دیتابیس سروری: دادهٔ واحد و هم‌زمان اما نصب، شبکه و ادارهٔ سرور لازم؛ (ج) SQLite روی هر دستگاه و sync آفلاین: نیازمند طراحی شناسه، conflict، حذف، زمان و reconciliation و پرخطرترین گزینه. پیشنهاد شروع **الف** فقط اگر شرکت تک‌دستگاه را بپذیرد؛ اگر LAN مشترک جزو الزام اولیه است، **ب** از آغاز، نه وعدهٔ تبدیل ساده در پایان. انتخاب نهایی باز است.

## ۲.۳ قرارداد امنیت و داده

1. آغاز نصب: ایجاد مدیر اولیه با رمز انتخابی، بدون credential پیش‌فرض. حساب‌ها با hash مقاوم مثل Argon2id، سیاست رمز و انقضای نشست؛ ورود با پاسخ خطای یکسان، محدودسازی تلاش و آزمون‌های رقابتی. سیاست نگهداری/انتقال هش PHP و بازیابی مدیر باید تعیین شود.
2. نقش‌ها: مدیر/کارمند با جدول مجوز قابل آزمون؛ **هر فرمان** خواندن حساس، نوشتن، تنظیمات، پشتیبان، چاپ/صدور و restore در Rust بررسی شود. مخفی‌کردن دکمه یا Tauri capability به تنهایی نقش کاربر را enforce نمی‌کند؛ actor هرگز از UI پذیرفته نشود. مجوز و نوشتن و رویداد در همان تراکنش با بررسی revision انجام شود؛ رفتار logout در برابر عملیات آغازشده صریح تعریف شود.
3. تاریخچه: شناسه و نام/نقش snapshot کاربر، زمان UTC، نوع/شناسهٔ سند، قبل/بعد یا diff، شمارهٔ رویداد و دلیل عملیات؛ بدون رمز/هش. restore و ورود اطلاعات و عملیات سیستمی actor و provenance دارند. اگر درج تاریخچهٔ الزامی شکست خورد، تراکنش رد شود. دسترسی audit مدیر و آزمون fail-closed. فایل محلی/مالک دستگاه نمی‌تواند به تنهایی امنیت ضد‌دستکاری کامل تضمین کند؛ اگر تأیید مستقل لازم است، امضای رمزنگاری و نگهداری برون‌دستگاهی/سرویس جدا و مدیریت کلید باید بررسی شود.
4. پشتیبان: snapshot سازگار با SQLite با Online Backup API یا `VACUUM INTO`، نه کپی دلخواه دیتابیس در حال تغییر [1](https://www.sqlite.org/howtocorrupt.html)؛ ذخیرهٔ نسخهٔ ایمنی، اعتبارسنجی نسخه/checksum/FK/مقادیر، آزمون بازیابی اتمی، فضای خالی، قطعی برق و عدم بازنویسی فایل. طرح رمزگذاری و بازیابی کلید/رمز پیش از استفادهٔ واقعی؛ محافظت OS و محل نگهداری هم ضروری است.
5. ورود داده: تنها منبع معتبر و به‌صورت صریح تأییدشده، محدود و audit شده؛ هرگز dump ناشناس SQL را در برنامه اجرا نکنیم. دادهٔ واقعی در مخزن، تست، لاگ یا CI ذخیره نشود.

## ۲.۴ بررسی اختیاری تبدیل MySQL → SQLite

کاربر شروع با معلومات تازه را انتخاب کرده است؛ **پیاده‌سازی import دادهٔ قبلی در محدودهٔ فعلی نیست.** نکات زیر صرفاً برای محفوظ‌ماندن تحلیل در صورت تغییر نیاز در آینده‌اند و نباید مانع شروع ساخت نسخهٔ محلی شوند.

1. نسخهٔ schema و charset/collation و خروجی `SHOW CREATE TABLE` نصب واقعی را ابتدا در محیط جدا بررسی کنیم. schema مخزن و دادهٔ نمونه الزاماً مشابه همهٔ نصب‌ها نیستند.
2. ابزار انتقال جداگانه، فقط خواندنی نسبت به منبع: استخراج ردیف‌های جداول شناخته‌شده از MySQL/MariaDB یا dump که در **محیط ایزوله و قابل اعتماد** بارگذاری شده؛ برنامهٔ اصلی مستقیماً SQL فایل ناشناس را اجرا نمی‌کند. از حساب فقط خواندن استفاده شود؛ هیچ credential در repo یا log نباشد.
3. فایل تبادلی نسخه‌دار با محدودیت اندازه و checksum، encoding UTF-8 و decimal به صورت رشته؛ نگاشت صریح enum، null، timestamp، ID و همهٔ ستون‌ها. شناسهٔ منبع و شمارهٔ سند حفظ شوند، جدول نگاشت `source_table/source_id → target_id` و provenance نگهداری شود. ناسازگاری‌های حذف مشتری/ماده/پرداخت‌کننده، orphan، نام‌های تکراری و دادهٔ قدیمی ناقص گزارش شوند؛ سکوت یا حذف ممنوع.
4. اعداد بدون float: `DECIMAL(16,2)` قدیم تا `99,999,999,999,999.99` را پوشش می‌دهد؛ به صدم در i64 جا می‌شود ولی سقف بسیاری از ورودی‌های نمونهٔ فعلی `1_000_000_000_000` صدم است. از `i128` برای ضرب/جمع و تبدیل کنترل‌شده به i64 استفاده شود. overflow، مبالغ منفی/صفر نامعمول و تفاوت مبلغ ثبت‌شده با محاسبه در گزارش مغایرت و نیازمند تصمیم‌اند، نه truncate یا تصحیح خاموش.
5. MySQL `utf8mb4_unicode_ci` و SQLite `NOCASE` یکسان نیستند (به‌ویژه غیر ASCII). normalization، حساسیت حروف و برخوردهای یکتایی با دادهٔ آزمایشی تعریف شود؛ متن خام از بین نرود.
6. سناریوی انتقال: بررسی read-only → staging تازه → گزارش تعداد هر جدول، کلیدهای بی‌ارتباط، مبالغ هر ارز و هر دوره، شمارنده‌ها و اختلاف‌های مانده → تأیید → snapshot ایمنی → commit اتمی/تعویض کنترل‌شده → دوباره بررسی و امکان بازگشت. ورود دوباره، دادهٔ تکراری، توقف وسط کار، نسخهٔ ناشناخته و کمبود فضای دیسک تست شود. **تطبیق با صاحب داده و حسابدار الزامی است.**
7. انتقال از `desktop/` آزمایشی یک مسیر جدا از PHP است؛ جدول‌بندی، شمارهٔ محلی، تاریخچه، کاربران و رفتار backup آن متفاوت‌اند. مسیر را بدون مشخصات و تست قطعی اجرا نکنید.

## ۲.۵ نصب، اجرا و کیفیت

- Windows x64 به عنوان مسیر اولیهٔ قابل بررسی، Tauri NSIS یا MSI؛ وضعیت WebView2 و نصب offline با کاربر تصمیم‌گیری شود. Tauri حالت offline installer برای محیط بدون اینترنت دارد ولی اندازه را افزایش می‌دهد [1](https://v2.tauri.app/distribute/windows-installer/). macOS/Linux فقط پس از تأیید سیستم‌های مقصد و آزمون آن‌ها.
- نصب‌کنندهٔ release/debug، معماری CPU و شمارهٔ نسخه مشخص؛ امضای واقعی نیازمند گواهی معتبر و مدیریت امن کلید است. تا آن زمان «بدون امضا»؛ فایل نصب آزمایشی و داده‌های آن نباید با نسخهٔ دیگر تداخل داشته باشند.
- CI مستقل پروژهٔ جدید: lint/typecheck، test React، property/unit Rust، migration و FK و restore، data import و differential، build Windows، smoke install/start/uninstall و artifact؛ قابلیت دسترسی/RTL/چاپ، native WebView و dialog و upgrade در محیط مناسب هم آزمایش شوند. تست مرورگر mock معادل تست Tauri نیست.

## ۲.۶ گام‌ها و خروجی هر گام

| مرحله | خروجی و شرط عبور |
|---|---|
| ۰. قرارداد | تکمیل ماتریس، حل موارد بحرانی سند ۰۴، schema نصب‌شده و fixtures بدون اطلاعات خصوصی؛ توافق هدف شبکه و حسابداری. |
| ۱. هستهٔ مستقل | اسکلت `farday-next` با شناسه/دیتابیس مجزا، CI و نصب آزمایشی؛ bootstrap، مدل داده و migration، بدون امکان دور زدن مجوز. |
| ۲. دادهٔ پایه | شرکت/ماشینری، lookupها، مشتری و کارمند با تمام فیلدها، تاریخچه و تست round-trip. |
| ۳. اسناد و حضور | فروش/رسید/مصرف/معاش و حضور با فیلتر، شماره، ویرایش/ابطال مورد توافق، اعداد دقیق، audit و تست هم‌زمانی. |
| ۴. حسابداری و راپور | کارت/مانده، دو حالت دخل، روزانه/ماهانه/سالانه، یادداشت و گزارش‌های تفصیلی، چاپ و CSV؛ differential و تأیید حسابدار. |
| ۵. انتقال و حفاظت | backup/restore و تست بازیابی؛ ابزار مهاجرت از PHP فقط در صورت تغییر نیاز و تأیید جداگانه. |
| ۶. پذیرش و توزیع | سناریوهای PHP در Windows Tauri واقعی، چاپ/دیالوگ/upgrade، تست خرابی و مقیاس؛ امضا در صورت گواهی و تأیید شرکت. |

هیچ مرحله‌ای با ساخت صرف UI یا موفقیت CI به تنهایی کامل اعلام نمی‌شود. هر مرحله شواهد، هشدارها و لینک آزمون دارد. برنامهٔ زمان‌بندی نیازمند پاسخ‌های سند ۰۴ و نتایج آزمون داده است.
